## Authoritative state and closed input

The host derives operator identity, active session, thread/turn/item/request identity, request kind,
command/path/host/permission summaries, expiry, exact app-server response, and all timestamps. The
browser supplies only the route IDs, expected approval revision, and one closed decision.

Every new turn uses approval policy `on-request` while retaining
`{type:"readOnly",networkAccess:false}`. This means ordinary sandboxed repository inspection may
continue without a side-effect prompt; a command that requests escape, a file change, managed
network access, or extra permission must cross this explicit gate. Accept never changes the
thread's default sandbox or approval policy.

File paths are normalized relative to the configured repository. File-change acceptance requires
the preceding `item/started` proposal and every changed path to resolve within the repository.
Filesystem permission acceptance supports only explicit path entries resolving within the
repository; unsupported/special/glob/outside-root requests are visible but not accept-enabled.
Network permission acceptance grants exactly the requested boolean for this turn. Mixed supported
filesystem/network requests grant no more than the normalized request. The repository path and raw
absolute paths are not repeated in approval storage or browser output.

## Behavior and transaction ownership

1. The app-server session validates a server request against the active external thread/turn,
   bounds all fields, classifies it, calculates a fingerprint, retains its exact response context
   only in the active process session, and emits a normalized approval event.
2. The conversation store transaction inserts or idempotently replays that request, changes the
   turn/conversation to `awaiting-approval`, increments conversation revision, and returns the
   public record. A duplicate external request with different fingerprint fails closed.
3. The stream publishes the durable approval. The app-server remains blocked waiting for its JSONL
   response; a two-minute server timer starts.
4. A decision transaction verifies operator/conversation/turn/approval ownership, active turn,
   pending status, expiry, `canAccept`, and expected approval revision. It records exactly one
   decision and operation audit before process dispatch. Simultaneous/duplicate/stale decisions
   converge on 409 and never write a second response.
5. The active session sends one exact protocol response. Command/file/network use the scalar
   one-request decision. Permission accept returns only the requested supported subset with
   `scope:"turn"`; decline/cancel returns an empty subset. Cancel also interrupts the turn.
6. Successful write moves `decided` to `dispatched`. `serverRequest/resolved` moves it to
   `resolved`; when no pending approval remains the turn/conversation returns to `running`.
7. Expiry atomically records `cancel`, sends the safe cancel/empty response once, and interrupts the
   turn. Turn cancellation/completion/process failure and host recovery close every unresolved
   approval as cancelled or failed. No prompt is replayed and no approval response is resent.

The database transaction cannot be atomic with the child-process side effect. The durable decision
is therefore committed first. If dispatch succeeds but final reconciliation fails, the record
remains decided/dispatched and all repeats conflict; the UI reports the uncertain terminal evidence
without claiming rollback.

## Failure, replay, and rollback contract

- Malformed/oversize/wrong-thread/wrong-turn/unknown approval methods are denied before persistence.
- Missing/wrong-operator records return 404; malformed IDs/body/decision return 400; stale,
  duplicate, expired, resolved, inactive, or non-approvable accept returns 409.
- A mismatched duplicate external request, process exit, dispatch failure, or terminal turn closes
  unresolved records without inventing rollback or resending a response.
- Same request/fingerprint replay returns its existing approval. Different data under the same
  request identity fails the turn closed.
- `decline` allows Codex to continue when app-server supports it. `cancel` and expiry interrupt.
- Any unsupported MCP elicitation, dynamic tool, generic user-input, token refresh, attestation, or
  legacy approval request remains denied and cannot be approved through this endpoint.

## Acceptance matrix

- Command, repository file change, managed network, and supported permission request each render
  bounded details and accept exactly once.
- Decline continues; cancel and expiry interrupt; `acceptForSession` and amendments never appear on
  the wire or in the UI.
- Outside-root/unsupported permission and file requests cannot be accepted.
- Wrong operator/turn/conversation, stale revision, duplicate click, already resolved, inactive
  session, malformed/oversize request, process exit between decision/dispatch, and restart all have
  stable outcomes with no second response.
- Request replay is idempotent only for the same fingerprint. Completion/resolution preserves
  durable decisions and activity without hidden reasoning, raw output, or patches.
- Existing local assistant behavior, read-only Codex history/cancel behavior, control security,
  three MCP verbs, catalog authority, and interaction-orchestration boundaries remain unchanged.
