## Authoritative state and closed input

All displayed state remains the exact current campaign/entity/component/content/action data already
loaded by the workspace. The only new input is one closed presentation key from the fixed set
`character`, `campaign`, or `combat`, generated by the component's own buttons or keyboard
navigation. Unknown keys are ignored. Callers cannot supply component values, derivations, effects,
visibility, revisions, action roles, or confirmation truth through view selection.

## Behavior, result, and typed effects

Character is selected on construction. Each view button is an HTML tab with one corresponding tab
panel, `aria-selected`, `aria-controls`, roving `tabindex`, and Left/Right/Home/End keyboard
navigation. Selecting a view hides the other two presentation containers and moves focus only for
keyboard navigation. Changing campaign, actor, encounter, or refreshing continues to hydrate every
existing panel so returning to a view shows current state.

`<dnd2024-character-sheet>` owns composition only. It has no shadow state, no request logic, no
calculation, and no action authority. This slice emits no typed effects and owns no transaction.
Existing controls continue to use their current server-owned effects and transaction contracts.

## Failure, replay, and rollback contract

- Missing/unknown component and partial-read failures retain the existing explicit panel states.
- An unknown presentation key produces no view change.
- View switching performs no network request, write, replay, or optimistic mutation.
- A failed refresh leaves error reporting with the existing workspace owner and does not persist a
  stale view or duplicate state.
- Existing action stale/replay/rollback behavior is unchanged because controls and bindings are
  moved, not recreated.
- No Scene, Knowledge, Map, image, attack, encounter-authoring, or tactical control is rendered as
  an empty promise.
