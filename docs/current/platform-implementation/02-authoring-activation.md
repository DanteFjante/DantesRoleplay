# 02 — Runtime authoring and recoverable activation

Status: proposed implementation plan. This document authorizes no runtime change by itself. Initial callers are the website and Codex through MCP, on one user-controlled installation. Other APIs remain extension points; device and provider bridges are excluded.

Prerequisite: implement [00 — Shared foundation](00-shared-foundation.md) first and have the coordinator supply its accepted foundation revision and contract baseline. This workstream consumes those shared contracts and does not redefine them independently.

## Outcome and existing owners

An authorized caller can create or revise information, schemas, queries, and JavaScript actions, validate the candidate, activate it within configured permissions, and inspect the resulting revision without rebuilding the host. Application behavior remains authored content; the kernel enforces generic storage, validation, execution, and authority boundaries.

Reuse [InformationStore](../../../src/system/information/persistence/InformationStore.cs), [MechanicStore](../../../src/system/mechanics/persistence/MechanicStore.cs), [the scoped ECS store](../../../DantesRoleplay.DataAccess/Ecs/SqliteApplicationScopedEcsStore.cs), and [schema validation](../../../src/system/schema-validation/persistence/BoundedJsonSchemaValidator.cs). Information records currently update their stored revision; mechanic definitions retain immutable versions. Neither fact establishes one consistent draft-to-activation lifecycle today. Information metadata currently receives bounded JSON-object checks; schema-declared validation requires explicit work.

[Registry administration](../../../src/system/registry-administration/persistence/RegistryAdministrationService.cs) already records registration and audit together. [Application activation](../../../src/system/application-activation/persistence/ApplicationActivationService.cs) validates an exact preview, expected active fingerprint, dependency evidence, and replay identity in a transaction. Its manifest retains document fingerprints and paths; retaining that manifest alone does not preserve changed source bytes. The proposed lifecycle must make runtime-authored revisions recoverable.

Extend these owners rather than create a replacement project: they already own authoritative records, dependencies, transactions, and audit. A parallel authoring registry would introduce competing identities and publication state without removing their responsibilities.

## Coordination and contract boundary

The coordinator establishes shared invocation and permission contracts before implementation. Every command carries trusted principal, scope, grant reference, definition revision, operation/parent identity, and budgets. Results carry outcome, data, commit evidence, and an optional task handle. These fields do not create another audit log.

Standing execute, author, and activate permissions are proposed additions; [current authorization](../../../src/system/authorization/domain/PrivateOperatorAuthorization.cs) has no durable grant store. The coordinator owns shared authorization contracts, database migrations, host registration, and cross-workstream wiring. This workstream owns candidate and activation behavior within existing subsystem files. Workstream 01 supplies execution validation; 03 supplies reuse discovery; 04/05 consume activation and grant evidence; 06 supplies website integration. No permanent runtime IDs are allocated here.

## Deliverable slices

1. **Define recoverable candidates and write preconditions.** After the shared baseline, identify each definition's existing owner and distinguish ordinary information updates from executable/schema publication. Add candidate revision, expected current revision, content fingerprint, origin, validation evidence, and activation disposition where missing. Preserve prior content needed for recovery; do not claim mutable information rows already provide immutable history. Extend information metadata validation against its declared schema with bounded resource use. Acceptance: concurrent edits reject stale expectations; an inert candidate is inspectable and cannot silently become active. Recovery: retries return the recorded outcome; rejected candidates remain available for correction.

2. **Validate compatibility and reuse before publication.** Use existing mechanic checks, catalog validation, schema validation, dependency inspection, and workstream 03 discovery. Validate source syntax, input/output contracts, declared service/effect permissions, referenced revisions, and bounded sample execution through workstream 01. Record the closest reusable alternatives and the reason for a new implementation. For schema changes, classify existing records and consumers; incompatible conversion requires a separately reviewed, data-preserving migration with explicit preconditions. Acceptance: an invalid dependency or incompatible stored record prevents activation with actionable evidence. Recovery: retain the prior active definition and original data; never erase incompatible values to make validation pass.

3. **Apply standing permissions at each transition.** Integrate the coordinator's policy with author, validate, activate, and execute operations. Check actual scope, allowed definitions/effects, current grant revision, and budgets; separate the ability to author from permission to publish or run. Automatically activate when the configured grant permits it. A denial returns a structured reason and leaves a usable candidate. Acceptance: a delegated caller can publish an allowed change without per-run approval, while grant revocation or a broader requested effect blocks the next dependent operation. Recovery: resume using fresh authority and validation; a candidate cannot amend its own grant.

4. **Publish one coherent active generation.** Extend exact-preview activation to runtime-authored definitions and retained content. Validate and prepare executable candidates with 01 before publication. Pin the candidate and dependency revisions; atomically record publication and its versioned change receipt within the activation owner. Content in another store must already be retained as an inert candidate; cross-store reconciliation is explicit, not an assumed shared transaction. Runtime caches and retrieval consumers derive recoverable refresh work from that receipt; embedding-provider availability cannot block authoritative publication. Running invocations keep their selected revision; new invocations resolve the exact active generation even if a derived cache must rebuild. Acceptance: a crash or replay produces one publication outcome, and an interrupted refresh cannot expose mixed revisions as a valid generation. Recovery: rebuild derived caches; restore a retained prior definition through a new validated activation. Restoring code does not undo committed data changes.

5. **Complete website/Codex authoring and synchronization.** Expose candidate, validation, permission explanation, activation, and recovery through existing generic services and the two initial callers. Reuse [CatalogExporter](../../../src/system/catalog/persistence/CatalogExporter.cs) and [CatalogImporter](../../../src/system/catalog/persistence/CatalogImporter.cs): export live changes before editing the same file-owned records; compare and import reviewed files only at an explicit synchronization boundary. Acceptance: both callers complete the same author-to-use workflow and obtain the same revision and receipt; conflicting file/database edits remain visible. Recovery: preserve divergent versions and require an explicit resolution, never automatic overwrite or data loss.

Each slice needs focused invariant verification; final acceptance includes the repository's full required checks and a protocol walk when MCP or dependency registration changes. Report results in the task, without a separate test inventory.
